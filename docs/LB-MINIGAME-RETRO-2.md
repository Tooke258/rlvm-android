# 小游戏（LBEX 棒球）第二轮复盘 — 2026-10-06 凌晨

> 上一轮复盘见 `docs/LB-MINIGAME-RETRO.md`。这一轮的目标本来是「把兼容层接上、让小游戏在真机上跑起来」，
> 兼容层做成了，但**小游戏本身仍然没进入可操作阶段**，而且我在后半程连续用「猜机制 + 打一包验证」
> 的方式试了两个假设（都失败）。本文把这轮的事实、弯路和下一条**有证据支撑**的路记下来。

## 2. 小游戏到底卡在哪（事实链）

1. 脚本在 `SEEN7300` 的帧循环里，循环体是「22 个实体各 `72/70/71` → `901`/`911` → `7350:12` → `7450` 检查」。
2. `SEEN7450:0190` 等 `intD[700]/[710]/[734]/[740] == 1`；其中 **`intD[700]` 全库只有 `SEEN7110` 的 `#entrypoint 0`（第 31 行）置 1**。
3. `SEEN7110` 后段（`:0087` / `:0154`）又要 **`intG[1900] == 1` / `intG[1901] == 1`** 才继续。
4. **整段真机 trace（12297 行）里 `intG[1900]/[1901]` 零次写入**，只有一次读。
5. **DLL 也只碰 `ctx+0x14`**（小游戏期间 33×CTXRD + 1×CTXWR，全是 intD 基址）→ DLL 不写 intG。
6. 脚本这段循环**从不调 `CallDLL(0,31/921/931)`**；我们 PC 上抓到的「真实帧」形态却是 `71×22 → 31 → 921 → 931 → 901/911`。
7. `CallDLL(1,…)`（EF00）在小游戏里 **0 次** → EF00 不在小游戏链路上（这条排除了）。

**卡点性质**：不是渲染、不是 PT00 算法、不是兼容层——是**「可操作阶段」的相位开关没人打开**。

## 3. 走过的弯路（要避免重演）

1. **用「猜机制 + 打一包验证」代替「先看基准事实」**。
   - 假设 A：原引擎在小游戏期间置 `intG[1900]/[1901]`。→ 先试「加载 DLL 时置位」（太晚：脚本第 87 行就检查了），再试「引擎启动时置位」→ **都无效**。
   - 假设 B：原引擎每帧替脚本补调 `CallDLL(0,31)`（用 `pt00_tick31=1` A/B）→ **也无效**。
   - 每轮都是 ~10 分钟的真机往返，只换来一个负结果。**正确做法是先拿「能正常玩的 PC 侧」的驱动序列与内存变化做基准。**
2. **被 [SKIP] 误导过**：我把「点中隐形按钮让剧情前进」当成小游戏跑起来了，实际是 PC 上的 [SKIP] 热区（用户当场指出）。
3. **重新翻旧账**：把「画面渲染不全 / `GetPattern` 0×0」这条早先的记录又翻出来查了一遍，而**本轮数据早就显示渲染是好的**（浪费了注意力）。
4. **一批 Sys opcode 被我用「容错占位」无脑跳过**（`150/210/211/215/216/436/441/446/451/456`）——语义未知就先跳过，等于埋雷：**它们里任何一个都可能是「写 intG/写相位标志」的那条**，而我却在这条不确定的地基上继续推理。
5. **`dump_scenes` 自己有 bug**：`SEEN.TXT` 里明明有 `7110/7450/7470/7500`（手写 TOC 解析确认 351 条非空），但诊断里 `archive.GetScenario()` 对这几幕返回空，我当时的结论「只出现一次读」有一部分是建立在这份不完整的 dump 上的（好在第 4 条用的是**整段执行 trace**，那条结论独立成立）。

## 4. 下一条该走的路（按证据强度排序）

**① 先确认「我们跑的脚本」和「用户实际在玩的脚本」是不是同一份**（不需要真机，今天就能做）

游戏目录里除了 `SEEN.TXT`(2008, 11.7MB, 351 幕，日文原版)，还有汉化补丁自带的一套脚本源：

```
lbex_sc.dll 里的字符串：; SEEN%04d / seen_sc.bin / seen_sc\*.txt / seen_sc\_*.txt / seen_sc_save.bin
```

也就是说：**PC 上跑的是补丁改写过的脚本（`seen_sc.bin` + `seen_sc\SEENxxxx.txt`）**，而 RLVM 读的是原始 `SEEN.TXT`。
如果小游戏那几幕在两份脚本里**语义不同**（比如相位标志换成了别的 intG/intD 下标、或者补丁顺手补了原版缺的引擎胶水），那么
——我们前面**整条「谁写 intG」的推理都建立在错误的脚本版本上**，再猜多少次也没用。

验证方法（便宜）：解析 `seen_sc.bin`（或 `seen_sc\*.txt` 覆盖文件）里 `7110/7450/7470/7500` 的内容，和 `SEEN.TXT` 的同名幕对比；
甚至先把 `seen_sc\SEEN*.txt`（如果存在）当作 RLVM 已有的 `SEEN####.TXT` 覆盖机制喂进去。

**② 如果脚本一致 → 在 PC 侧取基准（决定性）**

用 PC 端（小游戏能正常玩的那套）：

* 在 `PT00.dll` 的导出 `reallive_dll_func_call` 上下断点/打桩，**记录每帧引擎实际驱动的 func 序列**；
* 对 `intG[1900]/[1901]` 下**内存写断点**，看是谁写的（引擎本体？`lbex_sc.dll`？）；

有了这两份基准，Android 侧就不用猜了：缺什么补什么。

**③ 只在拿到基准之后再动「引擎胶水」**

把 `game_hacks.cc` 里那句 `LB_SkipBaseball`（`SEEN7030:15` → `ReturnFromFarcall`）当成**已知入口**，
按 PC 基准补出「进小游戏 / 每帧 / 出小游戏」三段行为，并且**只补证据支持的调用**。

**顺带要做的小修**（不阻塞上面）：

* 修 `dump_scenes` 的「取不到幕」问题（`GetScenario()` 为何对存在的幕返回空）；
* 把那 10 条「容错占位」的 Sys opcode 按**语义**实现（先从 PC 基准/补丁脚本取证），别再靠无脑跳过撑着。

## 5. 结论一句话

**兼容层这一层是成功的（真机在跑原版 DLL，且与原生逐位等价）；小游戏卡在「原引擎侧的小游戏胶水」上，
而我们一直缺的那份「基准事实」应该去 PC 端取，而不是继续在 Android 侧猜。**

## 6. 补充：把「基准事实」从原生引擎里挖出来了（同日稍晚，纯静态，不需要 PC 调试）

`REALLIVE.EXE`（2489344 字节，2.4MB 原生引擎）里带着四个导出名与 Gameexe 键：

```
@00632094 'reallive_dll_func_load'   @006320ac 'reallive_dll_func_init'
@006320c4 'reallive_dll_func_free'   @006320dc 'reallive_dll_func_call'
@00632014 '@^#DLL.%03d="%s"'（提示：DLL 必须和 RealLive.exe 同目录）
```

用 IDA 批处理（`tools/ida_find_dll_glue.py`、`tools/ida_xrefs_of.py`，复用 `.idb` 秒级出结果）顺着引用扒出调用链：

| 地址 | 作用 |
| --- | --- |
| `sub_42D6F0` | 读 Gameexe `#DLL.%03d` → `LoadLibrary` 的**加载器**；调用 `sub_42D840`（取 `func_load` 导出） |
| `sub_42D840/42D890/42D8E0` | `func_load` / `func_init` / `func_free` 的包装 |
| `sub_42D930(slot, func, a1..a4)` | **引擎自己的 CallDLL**：`GetProcAddress(hModule[slot], "reallive_dll_func_call")` 后转调 |
| `sub_4F01B0` | `sub_42D930` 的**唯一**调用者：取「DLL 名 → 槽位」（`sub_4A5BF0`）后带 func/4 参数调用 |
| `sub_4A6D50` | `sub_4F01B0` 的**唯一**调用者 → 即**脚本 CallDLL 指令的实现** |
| `sub_4A5BF0` | 「DLL 名 → 槽位」解析器，被 `sub_4A6980/4A6D50/4A9980/4AA870/4AB090`（各类 CallDLL 形态的指令）调用 |

**结论（推翻本文 §3 的两个假设）**：原引擎调用小游戏 DLL 的**唯一来源就是脚本的 CallDLL 指令**，
**不存在**「引擎每帧自动替脚本驱动 DLL」的机制 → 假设 B（补调 `CallDLL(0,31)`）在真值上不成立。
因此 `intG[1900]/[1901]` 的写入者**只能在脚本里**；而原始 `SEEN.TXT` 里它只读不写 →
**极可能我们跑的脚本（原始日文 `SEEN.TXT`）与你实际在玩的脚本（汉化补丁 `seen_sc.bin` + `seen_sc\*.txt`）不一致**，
补丁很可能在小游戏那几幕补了原版缺的相位逻辑。

**下一步**：解析 `seen_sc.bin`（或 `汉化补丁/` 下的 `seen_sc\*.txt` 覆盖），把 `7110/7450/7470/7500`
与 `SEEN.TXT` 的同名幕逐条对比，重点看 `intG[1900]/[1901]` 与 `intD[700..771]` 附近；若确认补丁脚本多了相位逻辑，
就把它作为 RLVM 的脚本覆盖（RLVM 本来就有 `SEEN####.TXT` 覆盖机制）喂进去再测。
