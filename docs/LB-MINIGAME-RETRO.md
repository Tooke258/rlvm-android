# 复盘：LB 小游戏「卡在 TIME」（2026-10-05）

> 背景：v0.2.4 之前小游戏是直接跳过的；`lb_minigame=1` 打开真路径后，一直走不通。
> 这份复盘的目的不是记录"我们做了什么"，而是回答"为什么花了这么多轮还没解决"，以及"下一步该换什么方法"。

## 1. 现状（按证据等级分开写）

### 已经确定、可以当结论用的

| 结论 | 证据 |
| --- | --- |
| PT00 是纯状态机，只通过 intD 与脚本交换数据，返回值恒 1 | M1 取证（45 调用点全表）+ 反编译 |
| PT00 的主线（10/11/12/30/31/60/61/910/920/921/930/931 + 类型 0 的 idx8 状态机 + 起球链）已按反编译移植 | `dev-log/PT00-M2A.jsonl`，编译与真机装机 |
| 工具链可用：Layer 1 符号化（142 条）、Layer 2 `codeex tables`（18 张真表）、PC 端可定位 intD 基址 | 见 §3，今天真的用上了 |
| 小游戏**不是**因为缺指令而卡死 | 补完 Sys151/152、Mem201、2:87 后，`Undefined: opcode` 刷屏彻底消失，但现象不变 |
| 小游戏**不是**因为快进/跳过被吞 | `[ff] ctrl=0 text_skip=0 forced=0` 全程只有一次状态变化（三个来源全 0） |
| 主循环**帧率正常**（≈60fps），在稳定地「60 帧 + 30 帧」循环后重来 | `[lb-loop]` 探针时间戳（30 帧 ≈ 0.49s） |
| 出口在 SEEN7100 的 `goto_unless (intL[0] == 0 || intD[3] == 1)`，`intL[0]` = `ReadExFrames(100)` 的返回值 | 脚本反汇编 |
| 该计数器是 `SetExFrames(100, 0, 60, 1000)`：60 帧 / 1000ms，步长 `1000/60 = 16.67ms` | 脚本 RAW 参数 + `frame_counter.cc` |

### 已证伪的假设（都曾被我当作结论，后被打脸）

1. **「Sel objbtn 是 M2 硬阻塞」** —— 不是。未实现指令只会跳过，不会中断。
2. **「`intD[71]` 没被同步是 bug」** —— 不是。模式 10/12 的分支完全不同，PC 上 `[71]=[70]-1` 是模式 12 那条分支每次重算出来的。
3. **「`FrameCounter::ReadFrame()` 结束后返回末值而非 0，是 RLVM 的 bug」** —— 不是。`ReadFrames` 会按 `IsActive()` 汇总，全结束才返回 0，语义正确。
4. **「Ctrl 卡键导致整段快进」** —— 不是。`[ff]` 探针三个来源全 0。
5. **「把 refresh 等待从 16ms 改成 17ms 就能闭合」** —— 不是。装上去仍然卡在 TIME。

## 2. 为什么花了这么多轮（方法论问题）

**问题一：主回路太慢。** 一直是「补一条指令 → 编译装机 → 请你手动试玩 → 我拉日志」。
单次往返 5–10 分钟，而每轮往往只前进一小步；一旦假设错了，这一轮就白烧。今天在这个回路上走了十几轮。

**问题二：我反复"拿局部证据下结论"。** 上面 5 条被证伪的假设，都是只看到一两个数据点就当成根因，
然后顺着它去改代码。正确的做法是**先让证据能自己说话**（比如把计数器内部状态打出来），再去改。

**问题三：最该先建的东西最后才建。** PC 端对照、intD 基址定位、探针这些"能一次给出决定性数据"的基础设施，
都是在你反复提醒之后才补上的；而它们一到位，立刻就把范围从"整个小游戏"缩到了"一个计数器的时序"。

## 4. PC 端对照的可用姿势（已验证）

```
1) x32dbg（**不是 x64**）附加 lbex_sc.exe（32 位）
2) 内存布局 → 找 pt00.dll 基址 B（实测就是 0x10000000，未重定位）
3) obj0 = [B+0x237C4]                     ← 实体对象指针
   obj[0] = [obj0+0]  = 0x1001D2A8        ← 自检：实体 0 的 vtable
   obj[1] = [obj0+4]  = intD 基址          ← 实测 0x01484F1C
   自检：obj[3] = 基址+0x348 = &intD[210]、obj[4] = 基址+0x3E8 = &intD[250]
```

反向（设备侧）我也能拿到同一片：加一个「导出 intD/intF 快照」开关即可。

## 5. 下一步建议（按性价比排序，前两条建议先做）

**A. 让计数器自己说话（最小、最决定性）**
在 `FrameCounter`（或 `EventSystem::GetFrameCounter`）上加一次性探针：每次 `ReadFrame()` 打出
`counter / value_ / max_value_ / is_active_ / ms_elapsed / num_ticks`。
一次试玩就能回答「计数器到底有没有在走、有没有走满、有没有被复位」——这正是现在唯一没被证实的一环。
**不做这个就继续改时序，等于继续猜。**

**B. 把「对照」变成逐帧 diff，而不是手抄 27 个数**
设备侧加开关导出 `intD[0..1999]` + `intF[0..1999]` 快照（二进制），PC 侧用已验证的地址同样导出。
然后写个 diff 脚本按帧对齐。今天手抄那 27 个数只能比较"一个瞬间"，不足以看出是哪一步开始分叉。

**C. 固定随机源，让重放可复现**
PT00 用了 `rand()`（起球角度/速度）；只要它参与流程，同一存档两次运行就会分叉。
给 PT00 的 `rand` 加一个可控种子（诊断开关），让"同存档 + 同步输入 → 同轨迹"成立，
之后才谈得上自动化回归。

**D. 时序对齐做成正式实现，别留魔数**
`refresh` 重载 1 现在是我按 16→17ms 猜的。正解是让"等一帧"与引擎自己的帧步长同源
（例如用 ex-frames 的同一时间基，或由渲染循环给信号），否则换个步长（30 帧段）还会以别的形式复现。

## 6. 明确先不做的事

* 不再"再补一条指令试试"——未知指令已经清空，剩下的都是时序/流程。
* 不再在设备上做"手玩 + 抄数字"式取证——那是最慢的回路。
* `主要人物没渲染` 这条单独立项：它属于实体渲染（`intD[1000+i*36]` 那套），
  与本复盘这条"演示不结束"是两回事，混在一起查会互相干扰。
