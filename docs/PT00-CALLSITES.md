## 1. 更正：62 个调用点里有 17 个属于 slot 1（EF00）

旧记录把「脚本里所有 `CallDLL`」都算成了 PT00。实际按槽位拆开后：

| slot | DLL | 调用点 | func 集合 |
| --- | --- | --- | --- |
| 0 | PT00（棒球） | **45** | 10 11 12 30 31 50 60 61 70 71 72 100 101 102 103 190 900 901 910 911 920 921 930 931 |
| 1 | EF00（特效） | 17 | 0 1 2 3 4 |

slot 1 的 17 个调用点（`SEEN9012` / `SEEN9057` / `SEEN9058`）用的是 `func` 0–4，
而 RLVM 里 **EF00 已经实现**（`systems/base/little_busters_ef00dll.cc`，
`0 = ConfigureEffect`、`1 = PerformCalculations`，另 2/3/4 为无参变体）。
这就解掉了上一轮的「func 0–4 不在 `func_call` 分发表里」的疑点——**它们本来就不是 PT00 的函数**。

结论：**PT00 侧不需要任何新工作**，M1/M2 只需盯 slot 0 的 21 个 func。

## 4. 五个问题的答案

### 4.1 调用契约

* 形参只有 `slot + func + 4 个 int`，**没有指针 / 内存块参数**。
* 真正的「共享内存」是**引擎的 intD 区**：`reallive_dll_func_load(a1,a2)` 内部把引擎传进来的
  上下文存进全局（`sub_10001060(dword_10023D18, a1)`），之后所有函数都用
  `*(*(ctx+0x14))` 取到 intD 基址，然后按**字节偏移**读写。
* 字节偏移 / 4 = intD 下标，这条换算在所有交叉点都对得上：
  * `func 900` 写偏移 7200 → **intD[1800]**，脚本紧接着在 7470:67 读 `intD[1801] / intD[1803]`；
  * `func 10/12` 写偏移 7600..7616 → **intD[1900..1904]**，脚本在 7410/7430/7470 立刻拿它摆 obj 坐标与缩放；
  * 实体表 `intD[1000 + i*36 + k]` 对应 DLL 里 `*(base + 4040 + i*144 + k*4)`。
* 对移植的意义：RLVM 侧只要 `machine.GetIntD()` 就够了，**不需要给 DLL 通道加新接口**。

### 4.2 渲染方式

DLL 完全不画。PT00 只导入 KERNEL32（MSVC 运行时符号），IDA 里没有任何 GDI/USER32 调用。
画面由脚本负责，用对象指令：`op<2:061:00010>`(objOn) / `op<2:071:01000>`(objLoad，资源名如
`PT_BALL01`、`PT_KAGE00`、`PT_TEA_CUP00`) / `op<2:081:01000>`(objSetPos) /
`op<2:081:01036>`(objSetZoom，取 `intD[1903]`/`intD[1904]`) / `op<2:081:01039>` /
`op<2:081:01004>`(objSetShow)。→ **不需要新增绘制接口**。

### 4.3 输入来源

DLL 不读输入。输入在脚本侧，走**引擎对象按钮（Sel objbtn）**：

* `SEEN7300` ep1：`op<0:002:00020>(2)` = `objbtn_init(2)` 建 2 个按钮 → `op<0:002:00022, 1>(2, 0)`；
* 结果经 `intD[90..96]`、`intD[46]` 分流（`intD[91..92]` 在 SEEN7921 写、`intD[93]` 在 SEEN7450 写）。

鼠标坐标本身（`op<1:004:00133>` GetCursorPos，全库 278 处）**没有出现在这 15 个棒球场景里**，
说明棒球的操作就是靠 objbtn。

⚠️ **前置阻塞项**：RLVM 的 `SelModule`（`modules/module_sel.cc`）只实现了
`select_w/select/select_s2/select_s/select_objbtn`(0–4) 与 `select_objbtn_cancel`(14)、`objbtn_init`(20)；
而 LBEX 还用到了 `op<0:002:00021>` `00022` `00023` `00030` `00032` —— 这些在 RLVM 里会走
`UnimplementedOpcode`。**M2 之前得先把这一组 objbtn 指令补上**（属于脚本模块层，
和 PT00 本身无关，但决定「能不能操作」）。

### 4.4 返回值语义

`reallive_dll_func_call` 的**每一条出口都是 `return 1`**（各 case 先调用处理函数再把 `result` 置 1，
`default` 也是 1）。全库 62 个调用点里 **0 处**把返回值 `<store>` 到变量
（`= op<2:001:00012` 命中数为 0）。

→ **脚本完全不看 DLL 返回值，DLL 的一切「输出」都通过 intD 副作用表达**。
M2 里 `CallDLL()` 一律 `return 1` 即可，不必关心返回值。

### 4.5 时序

是「每次调用推进一步」。证据（SEEN7470 结构）：

```
#entrypoint 0  -> 建 obj, 然后 CallDLL(0, 900)          # init
#entrypoint 1  -> 建 4 个场上角色 obj (PT_TEA00/...)     # 资源
#entrypoint 2  -> CallDLL(0, 901)                        # init 后半
#entrypoint 3  -> 读 intD[1800..1819] -> 60/12 -> 摆 obj # 每帧 tick
```

DLL 侧的 `900/901`、`910/911`、`920/921`、`930/931` 就是这个 begin/step 对；
`30/31` 是全局复位/主推进；`72`/`70`/`71` 是逐实体推进。
→ 我们的实现必须是**纯状态推进**（状态存在自己的 C++ 对象里，每调用一次走一步），
**不要**依赖引擎主循环钩子。
