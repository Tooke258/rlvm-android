## 0. 一页速读

**一句话**：小游戏最后能跑通，靠的不是"更聪明的猜测"，而是
**四件基础设施 + 一条纪律**；两次"卡死一整轮"都是因为当时没有它们。

| 要素 | 具体是什么 | 它换来了什么 |
| --- | --- | --- |
| 真值 | PC 端**原生 RL 引擎**的只读探针（A1–A4 锚点） | 把"观感/直觉"换成可对照的数字（D-040） |
| 门禁 | 与原版 DLL 的**逐位对照夹具**（280/280） | 每次改动都能自证"没退化" |
| 现场 | 观察点 + 环形缓冲（WATCH 环 / INTD 读环 / 调用环 / 内存窗口） | 崩溃与死循环能落到"哪一条指令、哪个变量" |
| 取证 | 崩溃处理器**链回系统处理器** + unwinder 回溯 | 真崩了能拿到 tombstone 与函数名，而不是"正常退出" |
| 纪律 | **先取证，再改一行**；一次只动一件事 | 避免"改得到处都是、但不知道是谁修好的" |

**两个改变全局的决策**（详见 §1.5）：D-039 放弃逆向功能补全、改走 DLL 兼容层；
D-040 用原生 RL 引擎做等位比较。

**当前状态**：里程碑已达成（小游戏不再卡 `time`、人物/球正常渲染、第一场跑完接上剧情），
遗留问题与下一步计划见 §6。

**怎么读**：只想接手干活 → §6 + `HANDOFF-2026-10-06.md`；

## 1.5 两个改变全局的决策

### D-039 放弃「逆向功能补全适配」→ 改走 DLL 兼容层

* **为什么放弃**：行为级重写进入**遍历循环** —— 每个卡点都要从脚本/内存反推 `func` 语义，
  收敛不了；而且被测对象是我们自己写的等价实现，**偏差不可证伪**（复盘 #1 的 5 条假设就是代价）。
* **改成什么**：在 Android 侧跑一个自研 **x86-32 执行器**，直接执行**用户游戏数据里的原版
  `PT00.dll`**（DLL 不进仓库 / 不进 APK）。
* **凭什么可行**：DLL 只有 159744 字节；可达代码约 4897 条指令 / 82 种助记符；无 SSE2，
  浮点是 x87（约 30 条）；契约极窄（`func + 4 int`，只共享 `intD`，返回恒 1）。
* **代价**：要维护一个 x86 解释器（PE 装载、KERNEL32 桩、假堆、x87 子集），
  并把"与真 DLL 逐位一致"当硬门禁。
* **得到的**：偏差全部收敛到宿主侧；`calls_long` 280/280、状态级 280 帧 0 差异、
  22 种实体单帧 22/22；最终真机跑通。

### D-040 用原生 RL 引擎做「等位比较」

* **为什么需要**：兼容层与原生的差异**不能用观感判断**（早期多次以观感下结论都被证伪）。
* **改成什么**：以 PC 端**原版 RL 引擎**为真值，按 A1–A4 锚点逐项对照：
  A1 对象/渲染栈、A2 脚本可见全局（`intD`/`intF` 整片）、A3 执行轨迹（幕/行/分支）、
  A4 DLL 调用序列与参数。
* **怎么做**：`tools/pt00_probe.exe` 只读扫内存（PC 侧真实进程是 **`lbex_sc.exe`**）+
  `tools/intd_diff.py` 逐项 diff + `tools/trace_loop.py` 抓循环 +
  `tools/g00_decode_probe.exe` 复核图像。
* **它换掉了什么**：把 5 条"看起来很像"的假设一次性判死；发现**脚本来源不同**；
  确认"挥棒判定 = `intD[101] == 1`"、"相机只由 `CallDLL(func=12)` 写"这类契约级事实。
* **留下的纪律**：**编码/约定必须用真值标定，不许猜** —— 当前方向键待办
  （`docs/INPUT-KEY-RECON.md`）就是这条的直接应用。

## 2. 十条经验（现象 → 为什么错 → 正确做法 → 工具）

### 2.1 不要从"崩溃瞬间的寄存器"推结论

死循环报错时打印的 `eax=0x17364D70` 看着像野指针，实际是循环里 `add $4,%eax` 累积的假象
（200M 步 ÷ 8 条/圈 × 4 字节 ≈ 1 亿字节）。入口现场（观察点 `pt00_watch=10004932` 记录）
是 `begin=0x11406E60`、`pos=0x11406E64` —— **只差 4 字节**。
**做法**：让工具记录**入口状态**并放进环形缓冲，崩溃时整环转储；不要事后用被污染的寄存器反推。

### 2.2 报错路径本身会吞掉现场

执行器自装的 SIGSEGV 处理器打印完寄存器就 `_exit(132)` —— 真机上只留下
`Zygote: Process N exited cleanly (132)`，**tombstone 一起没了**；而它打印的寄存器还是
**来宾**状态，宿主空指针时毫无用处。
**做法**：崩溃处理器**链回被替换的原处理器**（bionic/ART 那个才会叫 debuggerd），
raise 前先 `sigprocmask(SIG_UNBLOCK)`（处理期间本信号被自动屏蔽）；另输出一份不依赖
debuggerd 的宿主回溯（API 31 没有 `backtrace()`，用 `_Unwind_Backtrace` + `dladdr` 换算
**模块内偏移**）。**判据**：`exited cleanly (132)` 是我们自己的码，**不是正常退出**。

### 2.3 "野指针 / 内存被踩"经常是误读

同一个案例里我们先后下过两个错结论：①"begin/end 不自洽" ②"`heap_used=28000B`，
所以坏的 vector 不在堆上"。真相是寄存器被循环推歪、比较指令本身错了。
**做法**：先做一次**数量级算术**（步数 × 每圈字节数、指针差值是否 4 的倍数、
两个地址是否同一区间），再决定要不要怀疑"内存被踩"。这类算术往往 30 秒就能证伪一个假设。

### 2.4 夹具先建、再动手（等价性是可执行的门禁）

执行器从第一天起就有 `tools/pt00_oracle/compare.py`：同一串调用 + 同一随机种子，
分别喂给**真 DLL（oracle）**和我们的执行器，逐位比对返回值与 `intD` 改动。
本轮所有改动（含栈平衡、`cmp` 修复、x87 补齐）都是**先跑门禁再说**：`calls_long` 仍是
**280/280 逐位一致**。后来还加了指令级回归 `emu.exe --selftest`（`cmp` 大值寄存器比较、
x87 `fiadd m32int`）——把"曾经踩过的指令形状"固化成测试。

### 2.5 PC 原生引擎是唯一的锚点（编码/约定必须标定，不许猜）

A1–A4 四组锚点 + 只读探针 `tools/pt00_probe.exe`（PC 侧真实进程是 `lbex_sc.exe`）。
它给的是**契约级**事实，例如："挥棒判定 = `intD[101] == 1`"、"脚本里的 `intD[1900]/[1901]`
只由 `CallDLL(func=12)` 写"、"投手/打者在对象表里是 **children**"。
**做法**：凡是"某个值 / 某段编码代表什么"的问题，一律**先在真值侧做测量**再实现
（当前方向键待办就是这条的直接应用）。

### 2.6 上游引擎与 RLVM 的"宽严差异"是 bug 温床

同一个缺失的 Gameexe 键：原生 RealLive 取默认值（RLVM 自己代码里
`window_attr_mod_ == 0` 那一支就是"改用全局 `#WINDOW_ATTR`"），RLVM 却抛
`Unknown Gameexe key` → 窗口构造失败 → 永不进缓存 → 每帧重试每帧抛 → 阻塞 op
（`Msg 17 = pause`）永远完不成（真机 55Hz 空转、画面冻结、音乐正常）。
**做法**：把差异补在**平台层的数据**上（D-037，构造完 `Gameexe` 后补齐缺失键），
不动 `libreallive` 的解析语义；既不违反上游约束，又能让行为对齐原生。

### 2.7 补默认值时，只补"**没有默认值的**"那些键

第一版把 `TextWindow` 构造函数读的 13 个键全按"窗口 000 的同名值"照抄，
其中包括本来就有 `.ToInt(默认)` 的 `WAKU_SETNO / MOJI_SIZE / LUBY_SIZE / INDENT_USE /
R_COMMAND_MOD / NAME_MOD` —— 等于**改掉了原有行为**，把流程带偏、并顺手暴露了下一条
上游空指针。收窄成"RLVM 读取时没有默认值的键"之后立刻正常。
**教训**：一次修复的**范围**比修复本身更容易出事；"多补一点更保险"是错觉。

### 2.8 上游自己也可能有 bug —— 不要预设"一定是我的执行器错"

修完上面那条之后改成崩（`exited cleanly (132)`）；拿到 tombstone 才看清是
`TextWindow::Render` **先解引用、后判空**：
`text_window.cc` 341/449 行解引用 `namebox_waku_`，443 行才判空；而它只在
`NAME_MOD == 1 && NAME_WAKU_SETNO 存在` 时创建 → 窗口 032 没有 `NAME_*`，
一有说话人名（`GetNameSurface()` 非空）就空指针。
**做法**：当"宿主侧一切正常但仍在崩"时，用**符号化回溯**（§2.2）把最后一帧交给上游源码，
再决定是补数据还是给上游打补丁。

### 2.9 指令级 bug 的形状：只在特定代码形状下暴露

本轮四个宿主 bug 全是**语义细节**：
① 入口是 stdcall（`retl $0x14`），执行器返回后又清一次参数 → `esp` 每次 +20 字节
（8963 次调用后 `0x10200000 → 0x1022bc40`，20 × 8963 ≈ 0x2BC3C，算术闭合）；
② `cmp r32, r/m32`（`0x3B`）**寄存器形式**被截断成低 16 位 → `cmp %ebx,%eax; jne`
在两边都是堆指针时永远不等；
③ x87 `DA` 组（m32int 整数算术）整族未实现 → 每次 `UNIMPL` 让整个 CallDLL 中途放弃；
④ `DE` 组内存形式把 `reg == 0` 写成 `fp_pop()`（会毁掉 x87 栈）。
**做法**：真实调用序列 + **指令级自测**；遇到"看起来像内存被踩"的死循环，先怀疑
**比较/跳转/栈指针**这些"看起来最不会错"的指令。

### 2.10 "能画" ≠ "逻辑在跑"

真机日志里 **221 次** `[emu] 未实现指令 x87 @ 100033ed`（`da 46 4c` = `fiadd dword
[esi+0x4c]`）：每次撞上都让**整个 CallDLL 中途放弃**（不逐层 ret 直接返回），
于是画面还在动、球也像在飞，但每帧只有一半逻辑落地。
**做法**：把 `UNIMPL` / `GUEST FAULT` / `栈不平衡` / `步数上限` 这些计数当**廉价健康指标**，
每次真机跑完先看计数再看画面；"画面看起来对"从来不是证据。

## 3. 方法论：证据分级与熔断

### 3.1 证据分级（只有 A/B 级能用来下结论）

| 级别 | 例子 | 能证明什么 |
| --- | --- | --- |
| A · 真机日志 | `[pt00] 步数上限`、`rlvm-input: key code=273 pressed=1`、`frame content hash=… n=<非黑像素>`、`[lb-ext] input poll …` | "此刻发生了什么"，可计数、可对时间 |
| A · PC 真值 | `pt00_probe --full`、A1–A4 锚点 | "原生引擎此刻的状态是什么"，是判定谁对的标准 |
| B · 反汇编 | `llvm-objdump`、IDA、`build/rlvm-scenes.txt`（351 幕） | 存在性问题：**有没有**某个引用 / 写入 / 调用 |
| B · 夹具对照 | `tools/pt00_oracle/compare.py`（280/280） | "这次改动没让行为退化" |
| C · 单一日志顺序 / 观感 | "看到 `[SKIP]` 就以为小游戏没画"、"画面看着不对" | 只能用来**提出假设**，不能下结论 |
| D · 直觉 / 经验论断 | "这个值一定是脚本写的" | 同上，且最容易把人带进遍历循环 |

### 3.2 熔断规则（复盘 #1 之后定下，一直在用）

1. **同一假设连续 2–3 次实验都不成立 → 停**，写复盘换锚点；不要在遍历上继续消耗。
2. **一次只改一件事**，改完立刻跑门禁（夹具 / `--selftest`）+ 写日志；
   多改了东西时，宁可回滚重来。
3. 需要真机的实验**能合并就合并**（一次装机验多个问题）；不能合并时，优先做
   **不需要真机**的手段（探针 / 反汇编 / 夹具）。
4. 说出"我确定是 X"之前先自问：X 的证据是**哪一级**？能不能用一条日志或一个数字证伪？

### 3.3 我方四种失败模式（都真实发生过）

| 失败模式 | 实例 | 现在怎么防 |
| --- | --- | --- |
| 主回路太慢 | 装机 → 手玩 → 拉日志 5–10 分钟一轮，一轮只能排除一个点 | 先做"能自证"的工具（探针、夹具、观察点） |
| 拿局部证据下结论 | 把引擎自己的 `[SKIP]` 热区当成"小游戏没画" | 证据分级（§3.1）：C 级只用于提假设 |
| 基础设施最后才建 | PC 真值 / 逐位夹具都是"撞了墙才做" | 接入任何新模块，先把 §5 的清单走一遍 |
| 把"没观察到"当"不存在" | "没有任何地方写 `intG[1900]`" —— 实际是**脚本来源不同** + dump 工具自身有 bug | 先验证"我读的数据/我用的工具"本身对不对（§2.5 / §5 第 1、2 条） |

## 5. 接入清单（下次接"上游引擎 + 原版数据/脚本"时照做）

1. **先确认数据来源**：原版 ≠ 汉化补丁。LBEX 的教训是汉化补丁跑
   `seen_sc.bin` + `seen_sc\SEENxxxx.txt`，而我们读的是原始 `SEEN.TXT`，
   **同一幕的脚本内容与下标并不相同**（复盘 #2）。先回答"我在跑谁的脚本"。
2. **把看不见的状态变成数字**：写只读探针（内存/全局/对象表/帧计数），
   让内部状态能出现在日志里 —— 这是所有后续判断的前提。
3. **建两道门禁**：对**上游真值**（逐位对照夹具）与对**原生引擎**（A1–A4 锚点）。
   前者防退化，后者防"自认为对"。
4. **差异放在平台层**：上游引擎与 RLVM 的宽严差异（缺键、容错、默认值）
   一律用平台层的数据/开关解决，不改 `libreallive` / `machine` / `modules` /
   `encodings` 的语义；每处改动都要能单独审查。
5. **编码类约定一律标定**：键码、字符串编码、时间基、坐标口径 ——
   先在真值侧测，再实现（不许猜、不许从文档推）。
6. **崩溃与上报路径本身要留证据**：不要 `_exit()` 掩盖真相；不要吞异常；
   让系统 tombstone 能正常产生，并额外打一份模块内偏移回溯。

## 6. 当前待办与计划（截至 2026-10-06）

### 6.1 方向键 / 运动输入（已摸排，计划已定；细节见 `docs/INPUT-KEY-RECON.md`）

**已确认的前提**：① 平台侧链路是通的（pad → `keyEvent` → `PostKeyEvent` →
`EventSystem::DispatchEvent`）；② `DispatchEvent` 只交给注册的 listener 与**栈顶 long op**，
脚本执行期间按键被丢弃；③ 脚本从不轮询方向键（`Sys150/151/152` 的键码集合里没有 273–276）；
④ `Sys151/152` 的真实语义是"轮询给定键码表并写回引用"，我们只做了鼠标版、`Sys152` 恒 0；
⑤ `intD[109]` 是**死通道**（脚本无读取点 + DLL 无 `0x1b4` 访问），修它不会让移动生效。

**第一步（取证，不改代码）**：

| 实验 | 看什么 | 分支 |
| --- | --- | --- |
| A | 开输入栏按方向键，logcat 是否有 `rlvm-input: key code=273 pressed=1` | 没有 → Kotlin/pad 侧（pad 默认隐藏、触摸被 overlay 吃）；有 → 进 B |
| B | 同一次按是否有 `[lb-ext] input poll mouse -> …`、画面/光标是否变化 | 只有 key 日志 → 印证"当时栈顶不是 long op" |
| C | 只看光标（pad 每 60ms 发 `TOUCH_MOVE`） | 光标动而游戏无反应 → 游戏读的不是我们的光标，按修法 1 处理 |

**第二步（按性价比修，一次只做一件）**：

1. **让 `Sys151` 尊重键码表**（最小、最可能直接见效）。**硬约束**：必须保留现有鼠标语义
   —— `SEEN7420` 的挥棒判定是 `intD[101] == 1`，改坏它小游戏会再卡一次（历史回归点）。
   **键 → 值的编码必须用 PC 真值标定**：PC 同场景按键 + `pt00_probe.exe <pid> --full`
   抓 `intD[101]` 与变化槽位，测出来再写。
2. **引擎侧"方向键 → 光标移动"**（若要复刻原生手感）：平台层把
   `RLKEY_UP/DOWN/LEFT/RIGHT` 映射成 `InjectMouseMovement`，不依赖 long op。
   先按实验 C 确认 pad 的等价实现是否有效，避免重复劳动。
3. **`Sys152` 按键码表实现**（低优先级）：当前无消费者，但让 `intD[109]` 与原生一致。
4. **不要自创"脚本可读按键"接口**：RLVM 的 `src/modules/*` 里没有任何 RLKey/KeyState
   读取 op，`EventSystem` 也只存 shift/ctrl。原生真有这个通道，一定是我们还没实现的
   那批 Sys 号，应按"键码表"模型补，而不是发明新语义。

**验收判据**：夹具 `calls_long` 仍 **280/280**；VN 里 UP/DOWN 能翻页；
小游戏里"按住的键"能被轮询反映；挥棒判定不回归（`intD[101] == 1` 仍然成立）。

### 6.2 小游戏画面渲染三项（丢背景 / 实体缺失 / 卡顿）

* **丢背景**：先分清"没画"还是"画了被盖"—— 用 `dump_graphics` 图形栈转储看该层在不在、
  src/dst 是否 0×0；再与 PC 同点截屏对照图层顺序。
* **实体缺失**：以 A1 对象表为准逐项比对（本轮已用这条修掉"未播动画时 Gan 不渲染"）；
  重点看 children 与图层顺序，而不是只看"有没有这张图"。
* **卡顿**：先把耗时拆成三段 —— 执行器（每帧 CallDLL 次数 × 单次耗时）、渲染、合帧；
  再看是补执行器指令、减少每帧调用，还是动合帧策略。现成指标：
  `frame content hash=… n=<非黑像素>`、合帧耗时统计、`pt00` 的 func 直方图。
