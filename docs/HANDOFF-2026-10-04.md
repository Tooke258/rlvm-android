## 2. 本会话做完的事

### 2.1 动画"台阶感"排查 → 已定位、已移交（不再投入）

完整证据链见 **[`docs/FRAMERATE-INVESTIGATION.md`](FRAMERATE-INVESTIGATION.md)**，
决策见 `D-023`。结论摘要：

- 脚本 `SEEN9011` 用 `InitFrame(counter, 0, 10000, 1000)` 要求 **10000 级 / 1000ms**
  的平滑淡变；
- 实测只跑出 **8 级**（每级 ~125ms），因为脚本每圈调用的 `refresh()` 指令 =
  `GraphicsSystem::ForceRefresh()`，它在 `SCREENUPDATEMODE_MANUAL` 下执行
  `system().set_force_wait(true)`，而主循环 exec 的退出条件含 `!system.force_wait()`
  → **每轮提前结束**，一圈循环要 ~128ms 才转完。

**已在代码里改掉**（`exec_ignore_force_wait`，默认 true），但**用户叫停、未真机验证**。
用户判断这是 RLVM 自身的移植适配问题，打算另找高人接手，**本会话不再跟进**。

### 2.2 合成性能优化（`D-022`）

- 合帧改为脏标记驱动（`screen_needs_refresh()`，与上游 SDL 后端一致）；
- `AndroidSurface` 增加 `pixels_opaque_`（整面 alpha 全 255）→ `BlitToSurface` 走整行
  `memcpy`；**关键是目标侧状态要正确传播**（`DC0`/帧缓冲都是靠 blit 写入的，
  无条件失效会让快路径永远不命中）；
- `CaptureFrame` 只在内容哈希变化时调用，GL 线程不再每轮重传 1.9MB 纹理。

效果：静止场景 `loop dt` 6.2ms；动画场景合帧 16ms → 11ms/轮。

## 3. 【待办·重点】LBEX 存档：能写、读不到

### 3.1 精确症状（用户复述）

> "虽然有 save，但是重启之后 load 确实是空的。"

真机目录核对（`/sdcard/Android/data/org.rlvm.android/files/.rlvm/KEY_リトルバスターズ！ＥＸ/`）：

```
global.sav.gz    1046 B   05:44
save000.sav.gz   1382 B   05:44   ← 存档确实写进去了
```

**即：写入路径正常，重启后游戏内 LOAD 界面看不到这个槽位。**

### 3.2 本会话已查明 / 已改动

根因线索：`System::InvokeSaveOrLoad`（`src/systems/base/system.cc:451`）

```cpp
GameexeInterpretObject save_mod = gameexe()(mod_key);    // SYSTEMCALL_SAVE_MOD
GameexeInterpretObject save_loc = gameexe()(location);   // SYSTEMCALL_SAVE
if (save_mod.Exists() && save_loc.Exists() && save_mod == 1) {
  ... machine.Farcall(scenario, entrypoint);             // 路径A：游戏自带脚本
} else if (platform_) {
  platform_->InvokeSyscomStandardUI(machine, syscom);     // 路径B：引擎对话框
}
```

LBEX 的 `GAMEEXE.INI`：`#SYSTEMCALL_SAVE_MOD=0` + `#SYSTEMCALL_SAVE=9999,10`
→ 按上游逻辑走**路径 B**，而本移植**从没有 `SetPlatform`**（`platform_` 为 null）
→ 点击存档**静默无操作**。那个"目录建好却是空的"就是这么来的。

**本会话的改动**：无平台 GUI 时回退到路径 A（脚本路径）：

```cpp
const bool use_script_path =
    save_mod.Exists() && save_loc.Exists() &&
    (save_mod == 1 || platform_ == nullptr);
if (use_script_path) { ... Farcall ... } else if (platform_) { ... }
```

改了之后 `save000.sav.gz` 确实写出来了 —— **所以 save 这一半通了。**

### 3.3 还没查的（新对话从这里开始）

**症状是"写得到、列不出来"**，所以问题在**读取/列表**侧。候选假设，按可能性排序：

1. **LOAD 列表依赖未实现指令。** 本会话日志里 LBEX 有 6 条 `Undefined`：
   ```
   (SEEN9010)(Line 43): opcode<1:4:2055, 0>
   (SEEN9010)(Line 45): opcode<1:4:2056, 0>
   (SEEN9012)(Line 64): opcode<1:4:300, 0>
   (SEEN9012)(Line 65): opcode<1:4:1231, 0>
   (SEEN9012)(Line 66): opcode<1:4:3503, 0>
   (SEEN9024)(Line 1230): opcode<1:4:2005, 0>
   ```
   先确认这些 opcode 属于哪个模块、是不是存档界面用到的。
2. **存档元数据（`SaveGameHeader`）读写不一致。**
   `module_sys_save.cc` 里 `SaveExists(1409)` / `SaveDate(1410)` / `SaveTime(1411)` /
   `SaveDateTime(1412)` / `SaveInfo(1413)` / `GetSaveFlag(1414)` / `LatestSave(1421)`
   是 LOAD 界面列槽位的入口；逐个用 `trace=1` 看 LOAD 时哪一个返回了空。
3. **路径/命名不一致。** `buildSaveGameFilename()` 用
   `machine.system().GameSaveDirectory() / "save%03d.sav.gz"`；
   确认 LOAD 侧走的是同一个函数、同一个 `GameSaveDirectory()`。
   注意 `System::GameSaveDirectory()`（`system.cc:384`）有 Android 移植加的
   override 分支（`SetGameSaveDirectoryOverride`），历史上曾把它指到游戏目录又回退。
4. **`LatestSave` 的时间戳解析。** 它用 `fs::last_write_time` + `starts_with("save")`
   + `std::stoi(filename.substr(4, 3))`；确认 `.sav.gz` 的文件名长度与切片对得上。

**验证手段**：先 `trace=1` 跑一次"进 LOAD 界面"，看 `module_sys_save.cc` 里那几个
查询 opcode 的实际返回值；再对着 `SaveExists` 的实现单步核对。

参考：Kud Wafter 的存档链路是**通的**（见 `docs/PROGRESS.md` 第 8 节），
所以可以拿它和 LBEX 做对照——两者在 `GAMEEXE.INI` 里的存档配置是一样的，
差异应该在游戏脚本怎么用这些 opcode。
