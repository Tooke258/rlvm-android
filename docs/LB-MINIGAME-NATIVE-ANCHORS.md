# 小游戏排查 · 原生 RL 锚点对比方案（2026-10-06）

> 起因：小游戏在 Android（RLVM 移植）上停住，表现是**连打者在内的角色都不渲染**、屏幕上只有 [SKIP] 热区。
> 复盘教训：前几轮靠「读脚本 + 猜引擎行为」推进，效率低且出现过两次**拿名字/局部现象当证据**的误判
> （把 `PT_BAT00` 这个对象名当成「打者渲染了」；把被截断的 dump 当成「全库没人写 intG」）。
> 因此改为**锚点法**：先在原生 RL（能正常玩的那套）上固定若干「锚点」，再从移植侧取同样的量做逐点对比。

## 0. 锚点的选取原则

1. **必须是同一时刻**：用**同一段剧情/save**（建议就用用户当前那个卡在小游戏前的存档，PC 与 Android 各留一份同名快照）；
2. **必须是可机械读出的量**：不依赖观感（"看起来渲染了"不算证据）；
3. **优先选「脚本可见」的量**：脚本读什么，我们就比什么（这样差异一定指向引擎/移植差异，而不是美术差异）。

## 1. 锚点清单（四个，按优先级）

### A1 · 对象表（最重要，直接解释「角色不渲染」）

同一时刻，逐个对象读出：**槽位号 / 是否可见 / 目标矩形(x,y,w,h) / 源矩形(x,y,w,h) / 图案号 / 当前图像名 / Z 序**

| 侧 | 取数方法 |
| --- | --- |
| Android（RLVM） | 已有：图形栈转储（`[lb-ext] graphics tree`，含 `Rendering Rect`/`Clipping Rect`/`Image:`；跑在 select 等待时刻）。可扩展成机器可读的一行一对象（便于 diff） |
| 原生 RL | 用 Cheat Engine / x64dbg 按「对象数组基址 + 步长」遍历（先找基址：可用「已知对象数 220+」或图像名指针反查；也可以直接读引擎里 `GraphicsObject` 数组） |

对比目标：哪个槽位**原生可见而移植侧不可见**、或**原生有源矩形而移植侧是 0×0**。

### A2 · 脚本可见的整型状态（相位/标志）

`intD[70..95]`（相位一族）、`intD[700..771]`（小游戏阶段标志）、`intD[30]/[210]/[350]`、`intD[1800..1865]`（球）、`intG[1900]/[1901]`。

| 侧 | 取数方法 |
| --- | --- |
| Android | 已有：桥里每帧快照（`[pt00] frame N … phase 70..95=…`） |
| 原生 RL | Cheat Engine 读同一族地址（intD 基址可由脚本变量窗口或已知值反查） |

对比目标：**先确认这些量在两侧一致**——若一致，问题就纯在渲染侧（A1）；若不一致，才回头查脚本/引擎行为。

### A3 · 脚本执行轨迹（定位"该跑的没跑"）

同一段剧情里，两侧各自记录**执行过的语句**（含 farcall 目标）。

| 侧 | 取数方法 |
| --- | --- |
| Android | 已有：`trace=1` → `(SEEN####)(Line NNNN): <指令>` |
| 原生 RL | 在脚本 VM 的取指处下断点记录（或对 SEEN 场景切换/对象指令下断点抽样） |

对比目标：同一条剧情流，哪一条指令只在一侧出现（漏执行/多执行）。

### A4 · 小游戏 DLL 的调用序列（我们已有真值）

| 侧 | 取数方法 |
| --- | --- |
| Android | 已有：`[pt00] CallDLL func=…` |
| 原生 RL | 在 `PT00.dll` 的 `reallive_dll_func_call` 断点记录（或直接在引擎的 `sub_42D930` 断点） |

对比目标：**同一帧内 func 序列是否相同**（尤其 31/921/931 这类"主推进"是否被调用）。

## 2. 建议的执行顺序

1. 先做 **A2**（最便宜：一个存档、两边各读十来个整型）——若不一致，立刻回到脚本/引擎逻辑；
2. 再做 **A1**（最能直接解释症状）——重点看「角色对象」在两侧的 `visible` 与矩形；
3. 需要时补 **A3/A4**（我们已经各有一侧的真值，补齐另一侧即可）。

## 3. 本方案依赖的现有工具

* 全幕反汇编（351 幕，本地 `build/rlvm-scenes.txt`）：`dump_scenes=all` 生成；检索用 `tools/scene_search.py`
* 原生引擎静态取证：`tools/ida_find_dll_glue.py`、`tools/ida_xrefs_of.py`（对 `REALLIVE.EXE`，`.idb` 已建）
* Android 侧状态/图形/调用诊断：按帧快照、图形栈转储、`[pt00] CallDLL`、objbtn 诊断、ctx 读写取证
* PC 侧内存读取：Cheat Engine / x64dbg（用户本机已有）

### 3.1 PC 侧取数配方（A2：读 intD 一族）

原生侧先用 **Cheat Engine** 找到 `intD` 基址，之后所有 intD 下标都能直接算出来：

1. 走到**同一个锚点时刻**（小游戏的等待画面）；
2. CE 搜 `4 字节`、值 = **10**（= 我们真机快照里的 `intD[73]`，这个值当时是唯一的候选之一）；
3. 反复缩小：切一次场景再搜 10 / 或先改成别的值确认命中，直到只剩一两个地址；
4. 命中的那个地址就是 `intD[73]` 的地址 → **`intD 基址 = 命中地址 − 73×4`**；
5. 之后按 `基址 + 下标×4` 直接读：`70..95`（相位族）、`30/46/210/320/350`、`700/710/734/740/771`（阶段标志）、`1800..1804`（打者/投球）、`1830..1841`（球A）、`1850..1865`（球B）；
6. 把这些值填进下表与 Android 侧快照逐项对照（Android 侧现在的快照行已经包含这些字段，末段还带 `intG[1900..1901]`）。

> 提示：`intG` 是**另一块数组**（不在 intD 基址附近），首次进小游戏时它两侧都应为 0，所以 A2 阶段**不必**去 PC 侧找 intG；等 A1 做完、确认是渲染侧问题后再说。

| 锚点字段 | 原生 RL | Android（`[pt00] frame N …` 快照） |
| --- | --- | --- |
| `intD[70..95]`（含相位 73） | | |
| `intD[30]/[46]/[210]/[320]/[350]` | | |
| `intD[700]/[710]/[734]/[740]/[771]` | | |
| `intD[1800..1804]` / `1830..1841` / `1850..1865` | | |
| `intG[1900]/[1901]` | （首次同为 0，可不比） | |
