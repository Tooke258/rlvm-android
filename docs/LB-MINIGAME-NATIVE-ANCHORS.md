# 小游戏排查 · 原生 RL 锚点对比方案（2026-10-06）

> 起因：小游戏在 Android（RLVM 移植）上停住，表现是**连打者在内的角色都不渲染**、屏幕上只有 [SKIP] 热区。
> 复盘教训：前几轮靠「读脚本 + 猜引擎行为」推进，效率低且出现过两次**拿名字/局部现象当证据**的误判
> （把 `PT_BAT00` 这个对象名当成「打者渲染了」；把被截断的 dump 当成「全库没人写 intG」）。
> 因此改为**锚点法**：先在原生 RL（能正常玩的那套）上固定若干「锚点」，再从移植侧取同样的量做逐点对比。

## 0. 锚点的选取原则

1. **必须是同一时刻**：用**同一段剧情/save**（建议就用用户当前那个卡在小游戏前的存档，PC 与 Android 各留一份同名快照）；
2. **必须是可机械读出的量**：不依赖观感（"看起来渲染了"不算证据）；
3. **优先选「脚本可见」的量**：脚本读什么，我们就比什么（这样差异一定指向引擎/移植差异，而不是美术差异）。

## 1. 锚点清单（四个，按优先级）

### A1 · 对象表（最重要，直接解释「角色不渲染」）

同一时刻，逐个对象读出：**槽位号 / 是否可见 / 目标矩形(x,y,w,h) / 源矩形(x,y,w,h) / 图案号 / 当前图像名 / Z 序**

| 侧 | 取数方法 |
| --- | --- |
| Android（RLVM） | 已有：图形栈转储（`[lb-ext] graphics tree`，跑在 select 等待时刻）。**注意判据**：`GraphicsObject::Render()` 只在 `object_data_ != null && visible()` 时才输出该对象 → **转储里出现 = 这个对象确实被画了**；没出现 = 它没有 data 或不可见（A1 的「可见性」直接由此判定）。字段：`Object #N` / `Image: <名>` / `Rendering Rect(源) to Rect(目标)` / `Clipping Rect`+`After clipping` / `Properties`（alpha 只在 ≠255 时打印、mono/invert/tint/colour/composite/origin）/ `Mutators`。**暂缺**：图案号 `patt`、`z_order/layer/depth`（真要做 A1 时再补这两项即可） |
| 原生 RL | 用 Cheat Engine / x64dbg 按「对象数组基址 + 步长」遍历（先找基址：可用「已知对象数 220+」或图像名指针反查；也可以直接读引擎里 `GraphicsObject` 数组） |

对比目标：哪个槽位**原生可见而移植侧不可见**、或**原生有源矩形而移植侧是 0×0**。

### A2 · 脚本可见的整型状态（相位/标志）

`intD[70..95]`（相位一族）、`intD[700..771]`（小游戏阶段标志）、`intD[30]/[210]/[350]`、`intD[1800..1865]`（球）、`intG[1900]/[1901]`。

| 侧 | 取数方法 |
| --- | --- |
| Android | 已有：桥里每帧快照（`[pt00] frame N … phase 70..95=…`） |
| 原生 RL | Cheat Engine 读同一族地址（intD 基址可由脚本变量窗口或已知值反查） |

对比目标：**先确认这些量在两侧一致**——若一致，问题就纯在渲染侧（A1）；若不一致，才回头查脚本/引擎行为。

### A3 · 脚本执行轨迹（定位"该跑的没跑"）

同一段剧情里，两侧各自记录**执行过的语句**（含 farcall 目标）。

| 侧 | 取数方法 |
| --- | --- |
| Android | 已有：`trace=1` → `(SEEN####)(Line NNNN): <指令>` |
| 原生 RL | 在脚本 VM 的取指处下断点记录（或对 SEEN 场景切换/对象指令下断点抽样） |

对比目标：同一条剧情流，哪一条指令只在一侧出现（漏执行/多执行）。

### A4 · 小游戏 DLL 的调用序列（我们已有真值）

| 侧 | 取数方法 |
| --- | --- |
| Android | 已有：`[pt00] CallDLL func=…` |
| 原生 RL | 在 `PT00.dll` 的 `reallive_dll_func_call` 断点记录（或直接在引擎的 `sub_42D930` 断点） |

对比目标：**同一帧内 func 序列是否相同**（尤其 31/921/931 这类"主推进"是否被调用）。

## 2. 建议的执行顺序

1. 先做 **A2**（最便宜：一个存档、两边各读十来个整型）——若不一致，立刻回到脚本/引擎逻辑；
2. 再做 **A1**（最能直接解释症状）——重点看「角色对象」在两侧的 `visible` 与矩形；
3. 需要时补 **A3/A4**（我们已经各有一侧的真值，补齐另一侧即可）。

### 3.1 PC 侧取数配方（A2：读 intD 一族）

**首选：`tools/pt00_probe.exe`（只读扫另一个进程的内存，一条命令出结果）。**

```powershell
tools\build_pt00_probe.bat            # 只需编译一次（VS2022 + cl）
tools\pt00_probe.exe --selftest       # 自检：本进程里摆一份合成 intD 再扫自己 → 应打印 PASS
tools\pt00_probe.exe REALLIVE.EXE     # 真用：签名窗口模式（推荐）
tools\pt00_probe.exe REALLIVE.EXE 10  # 兜底：把 10 当作 intD[73] 逐值搜 + 邻居签名打分
```

1. 把游戏走到**同一个锚点时刻**（小游戏的等待画面）；
2. 跑 `tools\pt00_probe.exe REALLIVE.EXE`：它在目标进程里搜**连着的** `intD[70..76] = 20,19,15,10,0,-1,1`
   （单个值不够唯一——10 在 100+ MB 里能命中上千处；连着的 7 个值几乎唯一），
   命中后按 `intD[73] − 73×4` 反推基址，再把 A2 要的下标整段打出来；
3. 候选按「sane（`intD[0..1999]` 里有多少个像脚本变量的小整数）→ 邻居签名 → 地址」排序，
   取标着 `[最可能]` 的那条；`--selftest` 已把「找到 + 基址正确」这条链路验过；
4. 把候选块里 `intD[...]` 那几行**整段贴回来**，再与 Android 侧快照逐项对照。

工具只请求 `PROCESS_QUERY_LIMITED_INFORMATION / PROCESS_QUERY_INFORMATION | PROCESS_VM_READ`——**只读，不写目标进程**。
名字解析失败时会回显「枚举到几个进程 / 几个能打开」，用来区分「名字写错」和「权限不够」（沙箱账户看不到用户进程）。

**兜底：Cheat Engine**（工具因权限等原因跑不起来时）：搜 `4 字节` 值 `10`，反复缩小到一两个地址；
命中地址即 `intD[73]` 的地址 → **`intD 基址 = 命中地址 − 73×4`**；之后按 `基址 + 下标×4` 读那批下标
（`70..95` 相位族、`30/46/210/320/350`、`700/710/734/740/771`、`1800..1804`、`1830..1841`、`1850..1865`）。

> 提示：`intG` 是**另一块数组**（不在 intD 基址附近），首次进小游戏时它两侧都应为 0，所以 A2 阶段**不必**去 PC 侧找 intG；等 A1 做完、确认是渲染侧问题后再说。

| --- | --- | --- |
| `intD[70..95]`（含相位 73） | | |

子对象的 dst 落到父层裁剪窗口外，于是被裁掉。

### 6.1 位置从哪来：`CallDLL(func=12)` 写的「相机」

```
SEEN7340:  op<2:081:01000, 0>(203, 0, intD[1900] + intD[304], intD[1901] + intD[305])
           op<2:081:01036, 0>(203, 0, intD[1903])        ← AdjustVert
```

* `intD[1900..1904]` 在 351 幕反汇编里**没有任何赋值点**（`intD[1902]` 也只是被 `Sys 800`
  当**时间轴**读）；它们由 `CallDLL(0, 12, a1..a4)` 写。
* 用**真实 PT00.dll** 在 PC 上验证（`tools/pt00_oracle/oracle.exe` + 长夹具）：

```
func=12(-6000,0,3100,0) → intD[1900]=700  intD[1901]=790
func=12(0,0,0,0)        → intD[1900]=1300 intD[1901]=1100      ← PC 现场读到的正是这两个值
```

* 我们的 x86 执行器与 oracle **逐位一致（280/280）**，也就是说：**只要脚本调到了 func=12，
  安卓侧的相机值就会被正确写上**。

### 6.2 待判定：安卓这次到底有没有调到 func=12

之前 `[pt00] CallDLL` 日志只记**前 40 条**，而实体 AI 循环（70/71/72 ×22）正好把名额占满
（日志里只有 `72/70` 交替）—— 所以看不出相机调用有没有发生。已改成：

* 只记录 `func ∉ {70,71,72}` 的调用（上限 400 条）；
* 每 200 次调用打一行 **func 直方图**（`func histogram: 12x3 31x8 …`）；
* 帧快照新增 **`cam 1900..1904=`**（相机值；全 0 就意味着所有子对象的 dst 会落到屏幕外）。

## 7. 结案：两处**我们自己实现错了**，不是引擎差异

### 7.1 证据链

1. 直方图显示 `func=12` **确实被调用**，并且探针打印
   `cam after func=12 emu_changed=1 script_changed=1 now=1300,1100,0,0,0,`
   —— DLL 写了、兼容层也同步回脚本了，**相机没问题**。
2. 那么角色为什么仍在屏幕外？因为**相机是在这一帧的最后才写进去的**，而对象的 `objMove`
   在这帧开头就已经用旧的（0）算过了 —— 只要再跑一帧就会归位。
3. 但真机上**只跑了一帧**（直方图 70 次调用后就停在「等点击」）。顺着停住的地方查：

```
SEEN7420 line 212:  op<0:002:00030, 0>()     ← Sel 30
line 213:           intL[0] = <store>        ← 它返回一个值
line 213:           if (intL[0] < 0) { … }   ← < 0 = 点在「非按钮」处 = 挥棒

SEEN7310:  op<1:4:151, 0>(intD[101], 5, 4, 49, 0, 1, 2, 3, 100)   ← 输入轮询：写鼠标键
           op<1:4:152, 0>(intD[109], 81..89, 80)                  ← 输入轮询：写键位
SEEN7420:  if (intD[101] == 1) { …挥棒判定… }
```

4. 我们的两处实现：
   * `Sel 30/32` 被实现成 **push `ButtonObjectSelectLongOperation`（阻塞到点中按钮）** ——
     而真引擎里它是**非阻塞查询**（返回命中的按钮编号，点在非按钮处返回 -1）；
   * `Sys 151/152` 被当成「忽略参数」直接丢掉 —— 而它们是**每帧把输入写进 `intD[101]` /
     `intD[109]`**（`intD[109]` 全脚本只写不读，所以 152 先恒 0 也无害）。

   两条叠加 → 脚本第一帧就卡在 select 里 → 相机写进去了也没人用 → 屏幕上只剩背景/场地/数字。
   这也解释了「小游戏卡在 time」「只有点 SKIP 才推进」。

### 7.2 修复（只动我们自己的 LB 扩展层，没改上游语义）

* `ObjBtnSelect` 改成 `RLOp_Store_Void`：**非阻塞**，按当前鼠标位置命中 group 内按钮的屏幕矩形
  就返回该按钮编号，否则返回 -1；不再 push LongOperation。
* 新增 `LbInputPollOp` 取代 `lb_ignore_151/152`：解析第一个参数（`IntReference_T` 引用），
  把 `AndroidEventSystem::GetCursorPos()` 的左键状态（1=按住 / 2=刚抬起）写回去。

### 7.3 顺带确认的两个事实

* **PC 侧真引擎进程是 `lbex_sc.exe`**，它读的是 `seen_sc.bin`（汉化补丁脚本），
  而 RLVM 读 `SEEN.TXT`（原版）—— 两份脚本**不是同一份**（`seen_sc.bin` 头部就是自定义格式，
  和 `SEEN.TXT` 的 RealLive 归档格式不同）。这解释了整片 intD 里 99 处不同中的一部分
