# 小游戏（DLL）实现预案 —— 先讨论，再动手

> 状态：**草案，待讨论**（2026-10-05）。目标是把 LB / LBEX 的棒球小游戏从"跳过"变成"可玩"，
> 但这条线牵涉输入、渲染与一段闭源 DLL 的行为，必须先定路线和验收口径。

## 1. 已知事实（来自仓库现有勘察）

| 项 | 内容 |
| --- | --- |
| 现状 | `systems/base/little_busters_pt00dll.cc` 的 `CallDLL()` 只记录调用并 `return 0`（桩）；`machine/game_hacks.cc` 的 `LB_SkipBaseball` 直接把 farcall 返回掉，等于**跳过小游戏** |
| 入口 | 脚本 `SEEN7030` 第 15 行（`AddLineAction(7030, 15, …)`）；由 `SetLBSkipBaseball` 控制，诊断开关 `lb_minigame=1` 可以走进"真"路径 |
| 调用面 | PT00：**62 个调用点 / 21 个函数 / 15 个场景**（已枚举，见 `TASKS.md`） |
| 配置 | `GAMEEXE.INI`：`#DLL.000="PT00"`、`#DLL.001="EF00"` |
| 先例 | `EF00` 在 RLVM 里是"**结构真、数据伪**"的实现——说明"按接口形状模拟、内容自造"这条路线在本项目里已有先例 |
| 上游态度 | `game_hacks.cc` 原注释：不逆向 DLL 就"永远无法正确模拟"（所以上游选择了跳过） |

**取证手段（已备好，动手前先跑）**

1. `rlvm-diag.txt` 写 `lb_minigame=1` → 让脚本真正进入小游戏路径，`little_busters_pt00dll.cc` 的调用
   记录会把 `func` / 4 个参数 / 调用行号打进日志（logcat 与应用日志各一份）；
2. 用 `dump_scenario` 把 `SEEN7030`（及相关的 15 个场景）反汇编出来，看**脚本怎么用返回值**、每个
   `func` 的调用上下文——这是判断语义的主要依据。

## 2. 必须搞清楚的五个问题（决定工作量大小）

1. **调用契约**：`func` + 4 个 int 参数分别是什么？有没有"结构体指针/内存块"（用 `intG`/`intF` 当缓冲区）？
2. **渲染方式**：DLL 是**自己往屏幕上画**，还是**返回数据让脚本画**？前者要在移植层接一层绘制接口，
   后者只是数据搬运。
3. **输入来源**：DLL 读鼠标/键盘（还是读引擎内部状态）？决议案里的"可脚本化模拟输入"就是为这一项准备。
4. **返回值语义**：脚本按返回值分支吗？（62 个调用点里有多少是判定式的？）
5. **时序**：DLL 是否要求"每帧调用一次"（引擎主循环钩子）？如果是，我们得在引擎循环里留一个 tick 点。

## 3. 三条路线

| | A. 行为级重写（推荐起步） | B. 逆向原 DLL | C. 维持跳过 |
| --- | --- | --- | --- |
| 做法 | 用 dump 反推每个 `func` 的语义与数据流，用**我们自己的**输入/绘制把它重写出来 | 反汇编 `PT00.dll`，实现等价逻辑（必要时用 x86 模拟器跑原字节码） | 保持现状（`LB_SkipBaseball`），文档写清 |
| 保真度 | 中（能玩、过关口径一致；细节手感可能与原版不同） | 高 | 0 |
| 工作量 | 中（先 M1 取证，再按 func 逐个落地） | 高（且依赖用户提供 DLL） | 0 |
| 风险 | 行为偏差；需要脚本 dump 反复对照 | 法律/GPL 边界（**不打包**任何原 DLL，只做行为对照）；调试成本高 | 小游戏永远缺失 |
| 可测性 | 好——输入可脚本化，能做自动回归 | 差 | — |

**建议**：先走 A，把"能玩通"作为 v0.3.0 的目标；如果验收时要"手感一致"，再基于 A 的取证成果
评估是否加 B（B 的产物只用于对照，不进仓库）。

## 4. 分期与验收

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| **M1 取证** | 跑 `lb_minigame=1` + `dump_scenario`，把 21 个 `func` 的**参数形状、返回值用法、调用时序**整理成表（写进 `dev-log/PT00-RECON.jsonl`） | 能回答第 2 节五个问题，尤其是 1/2/4 |
| **M2 最小可玩** | 只实现"能开始 → 能操作 → 能判胜负 → 能返回脚本"这条主线（其余 func 先返回安全默认值） | 真机能从入口走到结束并正确回到剧情；日志里无未实现 func 的致命路径 |
| **M3 输入与绘制** | 按 M1 结论接输入（触摸/按键栏）与绘制（自绘或走引擎图层），并留**可脚本化的模拟输入**用于自动测试 | 手动可玩；自动脚本能重现一次完整对局 |
| **M4 对齐与打磨** | 逐个补齐剩余 func 的语义、得分/时间等数值对齐脚本预期 | 15 个场景全部走通；`lb_minigame=0`（默认）时行为与现在一致（可跳过） |

## 5. 需要拍板的三件事（讨论时定）

1. **路线**：A（行为级重写）/ B（逆向 DLL）/ 先 A 后评估 B？
2. **材料**：是否提供 PC 端 `PT00.dll`（仅用于**对照与静态分析**，绝不打包进仓库/APK）？
3. **验收口径**：目标是"**能玩通、剧情不断**"还是"**和原版手感一致**"？（直接决定要不要上 B）

> 未拍板前不动代码：默认行为保持现状（默认跳过小游戏、`lb_minigame=1` 才进真路径）。
