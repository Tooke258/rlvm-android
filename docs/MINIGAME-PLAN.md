# 小游戏（DLL）实现预案 —— 先讨论，再动手

> 状态：**草案，待讨论**（2026-10-05）。目标是把 LB / LBEX 的棒球小游戏从"跳过"变成"可玩"，
> 但这条线牵涉输入、渲染与一段闭源 DLL 的行为，必须先定路线和验收口径。

## 1. 已知事实（来自仓库现有勘察）

| 项 | 内容 |
| --- | --- |
| 现状 | `systems/base/little_busters_pt00dll.cc` 的 `CallDLL()` 只记录调用并 `return 0`（桩）；`machine/game_hacks.cc` 的 `LB_SkipBaseball` 直接把 farcall 返回掉，等于**跳过小游戏** |
| 入口 | 脚本 `SEEN7030` 第 15 行（`AddLineAction(7030, 15, …)`）；由 `SetLBSkipBaseball` 控制，诊断开关 `lb_minigame=1` 可以走进"真"路径 |
| 调用面 | PT00（slot 0）：**45 个调用点 / 21 个函数 / 15 个场景**；另有 17 个调用点是 slot 1 的 EF00（见 `docs/PT00-CALLSITES.md` §1） |
| 配置 | `GAMEEXE.INI`：`#DLL.000="PT00"`、`#DLL.001="EF00"` |
| 先例 | `EF00` 在 RLVM 里是"**结构真、数据伪**"的实现——说明"按接口形状模拟、内容自造"这条路线在本项目里已有先例 |
| 上游态度 | `game_hacks.cc` 原注释：不逆向 DLL 就"永远无法正确模拟"（所以上游选择了跳过） |

**取证手段（已备好，动手前先跑）**

1. `rlvm-diag.txt` 写 `lb_minigame=1` → 让脚本真正进入小游戏路径，`little_busters_pt00dll.cc` 的调用
   记录会把 `func` / 4 个参数 / 调用行号打进日志（logcat 与应用日志各一份）；
2. 用 `dump_scenario` 把 `SEEN7030`（及相关的 15 个场景）反汇编出来，看**脚本怎么用返回值**、每个
   `func` 的调用上下文——这是判断语义的主要依据。

## 2. 必须搞清楚的五个问题（决定工作量大小）

1. **调用契约**：`func` + 4 个 int 参数分别是什么？有没有"结构体指针/内存块"（用 `intG`/`intF` 当缓冲区）？
2. **渲染方式**：DLL 是**自己往屏幕上画**，还是**返回数据让脚本画**？前者要在移植层接一层绘制接口，
   后者只是数据搬运。
3. **输入来源**：DLL 读鼠标/键盘（还是读引擎内部状态）？决议案里的"可脚本化模拟输入"就是为这一项准备。
4. **返回值语义**：脚本按返回值分支吗？（45 个 PT00 调用点里有多少是判定式的？）
5. **时序**：DLL 是否要求"每帧调用一次"（引擎主循环钩子）？如果是，我们得在引擎循环里留一个 tick 点。

## 2.5 静态分析结论（2026-10-05，`llvm-readobj` 读导入/导出表）

真机与 PC 文件一致，直接读 PC 端（`G:\Little Busters! EX\Little Busters! EX`）：

| DLL | 大小 | 导入 | 导出 | 结论 |
| --- | --- | --- | --- | --- |
| `PT00.dll` | 159,744 B | **仅 KERNEL32**（全是 MSVC 运行时启动符号） | `reallive_dll_func_load`（RVA 0x11B0） | **纯状态机/数据 DLL**：不读输入、不画屏幕 |
| `EF00.dll` | 57,344 B | 仅 KERNEL32 | `reallive_dll_func_load`（RVA 0x10E0） | 同一类（RLVM 已有实现 = `rlbabel_dll.cc`） |
| `lbex_sc.dll`（汉化补丁自带） | 35,328 B | KERNEL32 + **USER32 + GDI32** + MSVCRT | — | 补丁的钩子，碰输入/绘制；与小游戏无关，本项目不用它 |

**这条结论把预案砍掉一大块**：PT00 不自己读输入、也不自己画屏幕 → 第 2 节问题 2/3 的答案是
「都不需要」：输入由**脚本**读引擎的鼠标状态再当参数传进来，画面由**脚本**用 GRP/obj 指令画。
也就是：

- 不需要新增「输入模拟层」（脚本侧的鼠标/按键服务我们已经提供）；
- 不需要新增「绘制接口」；
- 工作量收敛成**「按 `func` 重写状态机与数值」**，即路线 A 的 M1/M2 为主。

**工具（本机已就绪）**：NDK 自带 `llvm-readobj` / `llvm-objdump` / `llvm-strings`；
IDA Pro 8.3（`E:\BaiduNetdiskDownload\IDA\IDA_Pro_v8.3_Portable`，用 `idat.exe` 跑批处理）
+ x64dbg（`E:\DBG\snapshot_2026-05-27_12-11\release\x64`，32 位 DLL 用同级 `\x32`）。

## 2.6 M1 结论（2026-10-05：脚本全量反汇编 + PT00.dll Hex-Rays）

**正式产出 = `docs/PT00-CALLSITES.md`**（45 个调用点全表 + func↔IDA 处理函数对照 + intD 映射 + 实体字段表）。
要点如下：

1. **调用面更正**：62 个 `CallDLL` 里只有 **45 个是 PT00（slot 0）**，另 17 个是 **slot 1 的 EF00**
   （`func` 0–4，RLVM 已实现）。上一轮「func 0–4 不在分发表里」的疑点即此，**PT00 侧无额外工作**。
2. **第 2 节五个问题已全部有答案**：
   - **契约**：只有 `func + 4 个 int`，无指针/内存块；**数据全走引擎 intD 区**
     （DLL 从上下文取 intD 基址，**字节偏移 ÷ 4 = intD 下标**，三处交叉验证通过）。
     → 移植只需 `machine.GetIntD()`，不用加新接口。
   - **渲染**：DLL 不画屏幕，画面由**脚本**的 obj 指令画 → 不需要绘制层。
   - **输入**：DLL 不读输入；输入走脚本的 **Sel objbtn**（`op<0:002:00020..32>`）。
   - **返回**：`reallive_dll_func_call` **恒 `return 1`**，全库 0 处接收返回值 → 我们一律 `return 1`。
   - **时序**：`entrypoint 0/2 = init`、`entrypoint 3 = 每帧 tick`；DLL 的 `900/901`、`910/911`、
     `920/921`、`930/931` 就是 begin/step 对 → 实现写成**纯状态推进**，不依赖引擎主循环钩子。
3. **新增前置阻塞项**：RLVM 的 `SelModule` 只实现了 `objbtn_init`(20) 与 `select_objbtn`(4/14)，
   **缺 LBEX 用到的 21/22/23/30/32**，命中会走 `UnimplementedOpcode`。
   要先补这组 objbtn 指令（脚本模块层，不动 `libreallive`/`machine` 语义），「能操作」才成立。

## 3. 三条路线

| | A. 行为级重写（推荐起步） | B. 逆向原 DLL | C. 维持跳过 |
| --- | --- | --- | --- |
| 做法 | 用 dump 反推每个 `func` 的语义与数据流，用**我们自己的**输入/绘制把它重写出来 | 反汇编 `PT00.dll`，实现等价逻辑（必要时用 x86 模拟器跑原字节码） | 保持现状（`LB_SkipBaseball`），文档写清 |
| 保真度 | 中（能玩、过关口径一致；细节手感可能与原版不同） | 高 | 0 |
| 工作量 | 中（先 M1 取证，再按 func 逐个落地） | 高（且依赖用户提供 DLL） | 0 |
| 风险 | 行为偏差；需要脚本 dump 反复对照 | 法律/GPL 边界（**不打包**任何原 DLL，只做行为对照）；调试成本高 | 小游戏永远缺失 |
| 可测性 | 好——输入可脚本化，能做自动回归 | 差 | — |

**建议**：先走 A，把"能玩通"作为 v0.3.0 的目标；如果验收时要"手感一致"，再基于 A 的取证成果
评估是否加 B（B 的产物只用于对照，不进仓库）。
