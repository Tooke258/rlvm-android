# 小游戏「击球方向」这条线（2026-10-07 全程固化）

> 前置：`docs/SYS1005-BALL-ROOTCAUSE.md`（球不出现）、`docs/HANDOFF-2026-10-07.md`。
> 本文覆盖 10-07 白天到夜里这一段：从"球能出手但方向反了"一路查到
> "方向逻辑在模拟器里是忠实执行的，差别在触球相位"。
> **读完 §5「已作废的假设」再动手**，那里列的都是走过一遍的弯路。

## 1. 结论摘要

1. 小游戏里球的**方向计算（`PT00.dll` 的 `func 50`）在模拟器里执行是忠实的**：
   浮点链、标志位、角度→速度、尾部结果码、`cl` 闸门、`rand()` 抖动、`[624]`
   的 15°/帧阶梯，逐项与反汇编/手算一致。
2. **本线真正修掉的两个 bug 都不在 `func 50`**（见 §2）：一个是 `Sys 1005` 的
   语义（上游 RLVM 占位实现），一个是模拟器 x87 `fstp st(i)` 的目标槽取值顺序。
3. **PC 与手机唯一还剩的差别是"触球落在挥棒的哪一相位"** —— 即输入/节拍层
   （`intD[624]` 在触球那一刻的值），不是 DLL、也不是模拟器。
4. 顺带做成并保留下来的能力：**逻辑帧/渲染帧解耦**（`logic_hz`）、**定点 x87
   追踪**、**全指令追踪**、**定点条件跳转翻转**、**全库偏移扫描**。

## 2. 本线修掉的两个真 bug（均已真机验证）

| 提交 | 内容 | 症状 |
| --- | --- | --- |
| `14b5c38` | `module_sys.cc`：`Sys 1005` 从上游的 `(v1-v3)/(v2-v4)` 改成**两点距离** | 球永远不出现（脚本 `intL[0] < 35` 的"球到打者"判定恒成立 ⇒ 每帧复位） |
| `73af44c` | `tools/pt00_emu/emu.c`：x87 `fstp st(i)` 的**目标槽必须在 pop 之前取** | 球朝反方向飞（`intD[234]` = +1000 应为 −999；`sub_10001A00` 的归一化被写丢一层栈） |

两个 bug 的取证方式后来复用了很多次：**用 PC 原生引擎的实测值去反证**
（`docs/SYS1005-BALL-ROOTCAUSE.md` 有完整反证链）。

## 3. 逻辑帧 / 渲染帧解耦（`tools/rlvm-diag.frame38.txt`、`logic37.txt`）

- 实测：PC `intD[760]` 引擎帧 **59/s**，但球的推进只有 **1448 单位/秒** ⇒
  **原生逻辑帧 ≈ 37.5/s**（每帧步长 38.6 单位）；手机原本 **65.7 逻辑帧/s**
  ⇒ 同一段"投手→打者"1950 单位，PC 约 1.35 s、手机 0.77 s，**窗口只有 57%**。
- `frame_hz=N`：限制**整条主循环** —— ⚠️ 会把渲染一起压下去，实测还会与手机
  自身的 ~34/s 帧 tick 打拍（逻辑掉到 ~15 Hz）⇒ **不推荐**。
- **`logic_hz=N`（推荐）**：只给 `system.Run(machine)` 加节拍，渲染/抓帧每轮都做。
  按上述实测取 **37**。

| 9 | 「标志位/整数指令有实现问题」 | `fcomp → fnstsw(ah=01,C0) → test ah,41h → ZF=0 → 不跳`，与 x87 真实语义一致 |
| 10 | 「`frame_hz` 能解决节奏」 | 它压渲染、且与帧 tick 打拍 ⇒ 改用 `logic_hz` |
| 11 | 「`rand()` 取值域异常」 | 反推 `rand()` ≈ 20479…30309，落在正确 16 位域且逐球变化 |

## 6. PC 侧参照值（标准答案，改完用它验收）

- **一次正常安打**：球飞到 **(898, 496, 6646)**（右外野），`intD[264] = +983`。
- **击球方向两种都合法**：PC 扫描 16 次击球里多数 **+z 外野**、偶尔 **−z 身后**
  （如 `[264] = −304` 时球 z=788）⇒ **方向确实由触球棒角决定**，与 `[263]` 类别码无关。
- **挥棒角 `[624]`**：PC 与手机**同构**（`85 + 150k` 阶梯 → 球结束后复位 −215）。

### 9.2 两个方法论教训（都踩过）

1. **探针的 `using match #N (live copy)` 不可信**：同一时刻三份候选里，一份"去时间戳后
   不同取值数 = 2"（陈旧副本 —— 读它就会把正在打球的过程误判成"整段静止"），
   另一份 = 314（每帧在变 = 活动副本）。**必须用"去时间戳后不同取值数"判活动副本**；
   `tools/pt00_fast.exe` 的输出天然适合这个判据。
2. **PowerShell 的 `>` 会把输出写成 UTF-16**（解析全废）⇒ 抓日志一律 `cmd /c "... > file"`。

### 9.5 同轮闭环：外野回传落点（数据层）

**症状**：捕手/野手回传的落点比 PC 明显偏到**击球手身后**。

**根因**：`PT00.dll` 的目标点/本垒 `dword_10023D20/D24/D28`（文件初值 `0/0/0`）
由 **CRT 静态构造表**里的 `sub_10004AD0` 写成 `(0, 0, 2100)`：

```
.data 0x1001F004 起、6 项、以 0 结尾：
   10001070 100010b0 100010f0 10001130 10001170 10004ad0
10004ad0  jmp sub_10004AE0
10004ae0  xor eax,eax ; mov dword_10023D28,834h(=2100) ; mov dword_10023D20,eax ; mov dword_10023D24,eax ; retn
```

PC 用 `LoadLibrary` 加载 ⇒ Windows 跑 `DllMain → _CRT_INIT → _initterm`；
我们的执行器手工加载镜像、从 `func_load`(0x11B0) 起跑（`tools/pt00_emu/emu.c:1055`
注释写着"我们不跑 DllMain"）⇒ **整张构造表没执行** ⇒ 目标点停在 `0/0/0`
⇒ 回传瞄 z=0（击球手 z≈2100）⇒ 落点偏身后。

**修法与验证**：diag `pt00_run_ctors=1`（`tools/rlvm-diag.run-ctors.txt`）在 `func_load` 前补跑该表。

```
[pt00] ctor 10001070 ok … [pt00] ctor 10004ad0 ok
[pt00] CRT initializers attempted: 6
[pt00] peek 10023d20=0 10023d24=0 10023d28=2100
```
**用户真机确认回传落点恢复正常 ✓。**

> 注：同一张表的另外 5 项是 C++ 静态对象构造（3×`Iostream_init` + CRT 包装 + no-op）；
> `DllMain` 还写模块句柄 `dword_1002382C`（我们仍为 0，暂无消费者）。
> 探针/执行器侧的相关设置见 `tools/rlvm-diag.run-ctors.txt` 与 `build/pt00-ctors.txt`（反汇编快照）。
